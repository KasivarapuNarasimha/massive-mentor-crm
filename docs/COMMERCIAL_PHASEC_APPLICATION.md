# Phase C commercial application

## Implemented boundary
Dedicated quotation drafts, sealed pricing snapshots, immutable sent revisions, business-timezone QT numbering, explicit discount policy, revision-bound approval history and independent approvers are implemented. No self-approval, implicit manager authority, automatic grants or business/membership repair is allowed. All commercial arithmetic retains the Phase B canonical decimal-string/stacked-discount contract.

Secure sending uses an encrypted, leased durable outbox and a dedicated TLS-validating SMTP transport that never logs message bodies. Links contain a random 256-bit token in the Web URL fragment (`/quotation/review#...`), never the request URL. Only its SHA-256 is stored. Customer API requests carry the token in JSON POST bodies; no-cache/no-referrer/noindex headers apply. Decision-bound email OTPs have explicit tenant-configured expiry, persisted resend/attempt limits, constant-time HMAC validation and replay protection. At-least-once email delivery after a process/transport failure remains possible; conversion is exactly once.

Customer acceptance, OTP consumption, one unique conversion, invoice allocation and critical audit writes are in one Serializable transaction. Finance `sent` means Unpaid under the existing contract; no Payment is fabricated and paidAt is null. Mixed taxes remain in the immutable per-line snapshot; legacy scalar taxRate is zero and must never recalculate a commercial invoice. Existing Deal finance/Sales Orders require reconciliation instead of duplicate revenue. SaaS BillingInvoice/BillingPayment and subscription activation are untouched.

Manual payments maintain an append-only original/reversal ledger and the existing Payment mirror. Full/partial/reversed balances and status/paidAt are recalculated transactionally. Overpayment, foreign invoices, duplicate reversals and mirror drift fail closed. Legacy Finance mutation paths and SQL triggers protect commercial records. A composite tenant/invoice FK protects conversion linkage. Finance dashboard currency normalization excludes locked quotation invoices; aggregates exclude commercial records in other currencies with an explicit UI notice, and outstanding subtracts payments attached to open invoices only. The dedicated commercial report keeps exact balances separated by invoice currency. User deletion that would cascade-delete financial history is rejected.

Commercial routers are mounted before legacy repair-capable billing in index.ts through mountCommercialRoutes, shared with real PostgreSQL HTTP tests. Prefix misses terminate without falling through. Every authenticated operation pins an explicit x-business-id, then revalidates enabled exact membership, active business, module/action grants, resource/team scope and SELECT-only billing in its write transaction. A trusted configured invoice issuer is checked within a temporary same-tenant server context; the caller pin is restored and never replaced by client input. PostgreSQL serialization/deadlock conflicts, including raw SQLSTATE 40001/40P01, roll back and return 409 without automatic replay of partial writes. PostgreSQL can report conservative Serializable conflicts even across tenants; tests require the exact 409 conflict class and then explicitly retry the identical request/key after the concurrent operation finishes. No service automatically retries.

The operator page is /commercial. CRM Deals with explicit business/contact references link to it. Decimal values remain strings; displayed totals come from server snapshots. Expected versions and idempotency keys protect mutations. Uncertain payment retries retain the original timestamp/body/key. The page uses separate Finance grants for invoice/payment/report actions. Customer acceptance cannot be recorded by a salesperson.

## Configuration, no implicit defaults
Business.settings.commercial requires a policy version, configured two-decimal currency, valid IANA timezone, explicit enabled/disabled approval mode and any required zero-subtotal outcome. Threshold equality does not require approval; either configured exact percentage or same-currency amount exceeding its threshold does. Draft approval decisions become stale on policy changes; sent policy snapshots remain immutable.

Business.settings.commercialDelivery requires version, linkMinutes, otpMinutes, maxAttempts, maxResends, resendSeconds, invoiceDueDays and an enabled exact invoiceIssuerUserId with Finance/invoice.issue grants. GET/PATCH /api/quotations/configuration requires commercial.policy.manage; updates require an expected policy version, idempotency key and audit reason. No administrator or operational grants are provisioned automatically. Initial permission-manager provisioning needs a separately approved tenant-bound audited operation. Existing dedicated permission administration remains unmounted.

Environment names, not values: COMMERCIAL_PUBLIC_URL (HTTPS Web origin), COMMERCIAL_DELIVERY_KEY (base64 32-byte AES-GCM/HMAC key), SMTP_HOST/PORT/USER/PASS/FROM (465/587 with certificate validation), existing DATABASE_URL/JWT/environment requirements, NEXT_PUBLIC_API_URL (approved public API). Never put secrets in source or logs. Retain the delivery key while queued ciphertext/challenges remain valid; key rotation requires explicit queue/OTP handling. Zero-total invoice issuance remains fail-closed pending an explicit product rule. No payment gateway is implemented.
